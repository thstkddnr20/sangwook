TSID Long을 String으로 반환: JavaScript 숫자 정밀도 문제

64비트 정수인 TSID를 JSON 숫자로 내려주면 JavaScript 클라이언트에서 값이 깨지는 문제를 확인하고, API에서 문자열로 주고받도록 바꾼 사례입니다.

  • 문제 서버가 발급한 64비트 TSID를 JavaScript 클라이언트가 정확히 표현하지 못함
  • 원인 JavaScript의 Number는 약 9천조까지의 정수만 정확히 다룰 수 있어, 그보다 큰 TSID는 값이 깨짐
  • 해결 API 응답의 ID와 cursor, 경로 변수를 문자열로 주고받도록 변경

1. 문제 정의

채팅과 ACT 기록의 ID로 시간순 정렬이 가능한 64비트 정수인 TSID를 사용합니다. 이 값은 목록 응답의 ID뿐 아니라 페이지네이션의 cursor와 경로 변수(PathVariable)로 클라이언트와 서버 사이를 오갑니다.

그런데 JavaScript는 JSON 숫자를 모두 Number로 읽고, Number는 큰 정수를 정확히 표현하지 못합니다. 그 범위를 넘는 TSID는 읽는 순간 값이 달라집니다.

2. 원인 분석

같은 64비트여도 Java의 long과 JavaScript의 Number가 정확히 다룰 수 있는 정수의 범위는 크게 다릅니다.

언어 / 타입 상수 방식 정확히 다룰 수 있는 최대 정수
Java long Long.MAX_VALUE 64비트 정수 9,223,372,036,854,775,807 (약 922경)
JavaScript Number Number.MAX_SAFE_INTEGER 64비트 부동소수점 9,007,199,254,740,991 (약 9천조)

약 1,000배 차이가 납니다. TSID는 시간 순 정렬을 위해 상위 비트에 시간을 담기 때문에 10경이 넘는 값이 되고, Java에서는 문제가 없지만 JavaScript가 정확히 다룰 수 있는 범위를 넘어섭니다. 범위를 넘는 값은 가장 가까운 값으로 반올림되어 읽힙니다.

서버가 보낸 값 JavaScript가 읽은 값
1234567890123456789 1234567890123456800

서버가 발급한 ID와 클라이언트가 읽은 값이 달라지므로, 이 값을 cursor나 경로 변수로 서버에 되돌려 보내면 원래의 ID와 일치하지 않습니다.

3. 해결

ID를 숫자가 아니라 문자열로 주고받도록 API 계약을 바꿨습니다.

{ "id": 1234567890123456789 }

변경 전: JSON 숫자

{ "id": "1234567890123456789" }

변경 후: JSON 문자열

  • 응답에 담기는 TSID와 cursor를 문자열로 반환합니다.
  • 경로 변수로 받는 TSID도 문자열로 받도록 수정했습니다.
  • 변경한 API 계약에 맞춰 테스트 코드를 수정했습니다.

문자열은 어떤 JSON 파서에서도 값이 그대로 유지되므로, 클라이언트가 ID를 정밀도 손실 없이 서버에 되돌려 보낼 수 있습니다.

4. 회고

  • 서버 언어(Java)의 Long을 기준으로만 ID를 설계하면, 값을 소비하는 클라이언트의 숫자 표현 범위에서 깨질 수 있습니다. API 계약은 서버 관점이 아니라 소비하는 쪽 관점에서도 확인해야 한다고 생각합니다.
  • 64비트 정수 ID를 문자열로 내려주는 것은 이런 문제를 피하기 위한 일반적인 방식입니다. 클라이언트마다 JSON 파서가 다르더라도, 서버가 계약으로 안전을 보장할 수 있습니다.
