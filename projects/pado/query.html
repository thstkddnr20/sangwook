채팅 기록 조회 쿼리 성능 개선

채팅 기록 조회의 페이지네이션 방식을 검토하고 복합 인덱스를 설계해, 데이터가 쌓여도 조회 성능이 유지되도록 개선한 사례입니다.

  • 문제 데이터가 쌓일수록 OFFSET 방식은 앞의 행을 읽고 버려야 해서 조회가 느려짐
  • 해결 tsid 기반 커서 페이지네이션과 (user_id, tsid DESC) 복합 인덱스
  • 결과 조회 실행 시간 0.056ms → 0.017ms (약 70% 단축, 30회 반복 평균)

1. 문제 정의

채팅 기록 조회에는 페이지네이션이 필요합니다. 없다면 모든 채팅 기록을 한 번에 가져와야 해서, 데이터가 많을수록 응답 크기가 커지고 불필요한 데이터까지 전송되어 성능이 떨어집니다.

2. 설계 목표

채팅 기록 조회의 특성을 고려해 페이지네이션 방식을 골랐습니다.

  • 조회 패턴: 특정 페이지 번호로 이동하지 않고, 이전 대화를 위로 올려 가며 확인하는 무한 스크롤 구조입니다.
  • OFFSET의 한계: 페이지가 뒤로 갈수록 DB가 앞의 모든 행을 읽고 버려야 해서, 데이터가 누적될수록 응답 속도가 떨어집니다.
100만 건의 더미 데이터로 EXPLAIN ANALYZE를 확인했습니다. 인덱스가 없는 상태에서 OFFSET 10000 쿼리는 Parallel Seq Scan으로 조건에 맞지 않는 약 33만 건을 걸러낸 뒤 앞의 10,000건을 버리고 50건을 반환했고, 실행 시간은 61ms였습니다.
OFFSET 방식 실행 계획 확인하기 
SELECT *
FROM chatting
WHERE user_id = 10
ORDER BY tsid DESC
LIMIT 50 OFFSET 10000;
Parallel Seq Scan on chatting
  Filter: (user_id = 10)
  Rows Removed by Filter: 329,957
Execution Time: 61.332 ms

그래서 마지막으로 조회한 레코드를 기준으로 다음 데이터를 요청하는 커서 방식을 목표로 삼았습니다.

3. 해결

1) 커서 방식 페이지네이션

마지막으로 조회한 레코드의 tsid를 cursor로 사용해, 그보다 이전에 생성된 데이터만 조회하도록 쿼리를 바꿨습니다.

SELECT *
FROM chatting
WHERE user_id = ? AND tsid < :cursor
ORDER BY tsid DESC
LIMIT 50;
  • 앞의 모든 행을 읽고 버리는 스캔이 사라집니다.
  • 새 채팅이 실시간으로 추가되어도 중복 조회나 누락이 생기지 않습니다.
  • tsid는 시간순으로 정렬되는 고유 ID라서, 정렬 기준과 cursor를 별도의 컬럼 없이 함께 쓸 수 있습니다.
  • cursor가 없는 첫 요청은 Redis 캐시에서 최신 채팅을 먼저 찾고, 비어 있으면 DB를 조회합니다.

2) 복합 인덱스 추가

조회 조건인 user_id와 정렬 기준인 tsid DESC를 함께 고려해 복합 인덱스를 추가했습니다. 특정 사용자의 채팅 기록을 풀 테이블 스캔 없이, 인덱스로 필요한 범위만 읽어 가져올 수 있습니다.

CREATE INDEX idx_chat_user_tsid
ON chatting (user_id, tsid DESC);

복합 인덱스는 컬럼 순서가 핵심

등호 조건 컬럼(user_id)을 앞에, 정렬 기준 컬럼(tsid)을 뒤에 두는 것이 원칙입니다.

인덱스 순서 조회 시 동작
(user_id, tsid DESC) (왼쪽 표) 같은 user_id 안에서 이미 tsid 순으로 정렬되어 있어, 필요한 50건만 순서대로 읽음
(tsid DESC, user_id) (오른쪽 표) tsid 순으로 훑으면서 user_id를 다시 걸러야 함. user_id가 흩어져 있으면 비효율적이고, 분포에 따라 풀 테이블 스캔이 더 나을 수도 있음

4. 적용 결과

인덱스 적용 후에는 (user_id, tsid DESC) 복합 인덱스로 두 조건이 Index Cond에서 함께 처리되어, 불필요하게 버리는 행이 사라졌습니다.

커서 방식 쿼리 실행 시간 (30회 평균)
인덱스 적용 전 0.056ms
인덱스 적용 후 (user_id, tsid DESC) 0.017ms (약 70% 단축)
단일 EXPLAIN ANALYZE 결과는 캐시 워밍업 상태나 순간적인 시스템 부하에 따라 값이 튈 수 있어서, 쿼리를 30회 반복 실행한 평균값을 기준으로 비교했습니다.

5. 회고

  • 데이터가 늘어나도 안정적으로 동작하는 구조를 고민했습니다. 무한 스크롤이 사용성 면에서 유리하다고 판단해, 대용량에서도 일관된 성능을 유지하는 커서 방식을 선택했습니다.
  • EXPLAIN ANALYZE로 쿼리가 내부에서 어떻게 동작하는지 확인했습니다. OFFSET은 겉으로는 동작해도 내부적으로 대량의 행을 읽고 버리고, 복합 인덱스는 컬럼을 묶는 것에서 끝나지 않고 순서 자체가 읽는 범위를 결정한다는 것을 수치로 확인했습니다.
  • 앞으로 쿼리를 작성할 때 실행 계획부터 확인하는 습관을 들이려 합니다.
