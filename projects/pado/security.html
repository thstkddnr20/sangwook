배포 직후 스캐너 요청 관측과 nginx 단 차단

배포 직후 접속 로그에서 설정 파일(.env)을 찾는 자동 스캐너 요청을 확인하고, 애플리케이션에 닿기 전에 nginx에서 차단하도록 개선한 사례입니다.

1. 문제 정의

공개 IP에 서비스를 배포하면 특정 서비스를 노린 게 아니어도 자동화된 스캐너의 대상이 됩니다. 배포 직후 접속 로그에서 한 IP가 몇 초 사이에 /.env, /public/.env, /app/env 등을 경로만 바꿔 가며 연달아 요청하는 것을 확인했습니다. .env에는 DB 비밀번호나 API 키가 들어가는 경우가 많아서 스캐너가 가장 먼저 찾는 파일입니다.

45.119.212.x - - "GET /.env HTTP/1.1" 401 90 "-" "Mozilla/5.0"
45.119.212.x - - "GET /.env HTTP/1.1" 404 162 "-" "Mozilla/5.0"
45.119.212.x - - "GET /public/.env HTTP/1.1" 401 90 "-" "Mozilla/5.0"
45.119.212.x - - "GET /app/env HTTP/1.1" 404 162 "-" "Mozilla/5.0"

규칙 적용 전 access.log 발췌 (IP 일부 마스킹)

당시에는 nginx에 별도의 차단 규칙이 없어서, 이런 요청도 일반 요청과 똑같이 처리되어 401/404로 응답이 나가고 있었습니다.

  1. 설정·버전관리 파일을 노리는 요청이 차단 없이 처리됨
    • 이번 응답에는 파일 내용이 담기지 않았지만, 요청을 처리한다는 것 자체가 노출 표면입니다. 설정 하나만 잘못돼도 그대로 침투 경로가 됩니다.
  2. 스캔 요청이 정상 요청과 같은 access.log에 섞임
    • 로그가 스캔 요청으로 채워지면 실제 사용자 요청과 이상 징후를 구분하기 어려워집니다.
  3. 인증 없이 접근 가능한 로그인 경로가 반복 요청에 열려 있음
    • 인증 전 단계의 경로는 무차별 대입 시도의 대상이 될 수 있습니다.

2. 설계 목표

애플리케이션이 제공할 이유가 없는 경로는 앱에 닿기 전에 nginx에서 끊어야 합니다. 차단된 요청도 기록은 남기되 정상 요청 로그와는 구분되어야 하고, 인증 없이 열려 있는 진입점에는 요청 속도 제한을 두어야 합니다.

3. 해결

이 문제를 관측, 차단, 분리 기록 순서로 해결하였습니다.

1) 차단 - 점(.)으로 시작하는 경로를 nginx에서 403 처리

.env, .git, .config.yaml처럼 점으로 시작하는 파일은 웹 서비스가 외부에 제공할 대상이 아닙니다. 이 패턴의 경로를 정규식 location으로 잡아서 앱으로 프록시하지 않고 nginx에서 바로 종료합니다.

location ~* /\. {
    deny all;
    access_log off;
    log_not_found off;
}

2) 분리 기록 - 차단은 error.log, 앱 전달 여부는 upstream_time

차단된 요청은 이 location에서 access.log를 끄고, nginx가 access forbidden by rule로 error.log에 남깁니다. 정상 요청이 쌓이는 access.log에는 upstream_time을 함께 기록하도록 로그 형식을 바꿔서, 값이 있으면 앱까지 전달된 요청이고 -이면 nginx에서 끝난 요청으로 구분할 수 있게 했습니다.

[error] ... access forbidden by rule, client: 213.209.159.x, server: pado-anxiety.site, request: "GET /.env HTTP/1.1"
[error] ... access forbidden by rule, client: 213.209.159.x, server: pado-anxiety.site, request: "GET /backend/.env HTTP/1.1"
[error] ... access forbidden by rule, client: 213.209.159.x, server: pado-anxiety.site, request: "GET /.env.example HTTP/1.1"
[error] ... access forbidden by rule, client: 213.209.159.x, server: pado-anxiety.site, request: "GET /frontend/.env HTTP/1.1"

규칙 적용 후 error.log 발췌 (IP 일부 마스킹)

3) 제어 - 로그인 경로 요청 속도 제한

인증 없이 호출되는 로그인 경로에는 IP당 요청 속도를 제한했습니다.

limit_req_zone $binary_remote_addr zone=login:10m rate=10r/s;

location ^~ /login/ {
    limit_req zone=login burst=5;
    limit_req_status 429;
    proxy_pass http://127.0.0.1:8080;
    ...
}

4. 적용 결과

규칙 적용 전 규칙 적용 후
/.env 요청 응답 401 / 404 403
처리 위치 별도 차단 규칙 없음 nginx location 규칙에서 종료
기록 위치 access.log error.log (access.log에서 제외)

발췌한 error.log 기준으로 이 규칙이 차단한 요청은 45건, 출발지는 9곳이었습니다. 그중 30건은 한 IP가 14초 동안 /laravel/.env, /.env.production, /.env.bak처럼 흔한 경로 목록을 순회한 것으로, 모두 앱에 닿기 전에 nginx에서 종료되었습니다.

5. 회고

이번 스캔은 특정 서비스를 노린 공격이 아니라 공개 IP에 올라온 서버라면 누구나 받는 자동화 요청이었습니다. 다만 로그를 직접 읽어 보기 전에는 우리 서비스가 어떤 요청에 어떻게 응답하고 있는지 알지 못했고, 설정과 인증이 조금만 비어 있어도 곧바로 침투 경로가 될 수 있다는 점을 실제 요청으로 확인한 것이 가장 큰 소득이었습니다.

또한 이 규칙은 스캐너가 노리는 경로 중 점(.)으로 시작하는 것만 막습니다. 경로 패턴 차단은 알려진 시도에 대한 대응이고, 근본적인 방어는 애플리케이션이 외부에 여는 경로를 최소화하고 인증 없이 열린 경로를 목록으로 관리하는 것이라고 생각합니다. 그래서 인증 없이 열려 있는 경로 전체를 다시 점검하는 것을 다음 과제로 남겨 두었습니다.
