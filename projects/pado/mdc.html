요청 ID로 nginx 접속 로그와 앱 로그를 한 요청으로 연결

nginx가 요청마다 생성한 고유 ID를 애플리케이션의 MDC로 이어받아, nginx 접속 로그와 앱 로그를 같은 ID로 조회할 수 있게 한 사례입니다.

1. 문제 정의

요청은 nginx를 거쳐 Spring 애플리케이션으로 전달되고, 두 곳은 각자의 로그를 남깁니다. 이 로그들을 연결하는 기준이 없으면 한 요청의 흐름을 확인하기 어렵습니다.

  1. nginx 접속 로그와 앱 로그를 같은 요청으로 묶을 수 없음
    • 두 로그에 공통 키가 없으면 경로와 시각으로 짐작해서 대조해야 합니다. nginx가 기록한 응답 시간이나 상태 코드와 앱 내부에서 발생한 로그를 함께 보기 어렵습니다.
  2. 동시에 처리되는 요청의 앱 로그가 섞임
    • 요청은 스레드 풀에서 동시에 처리되어 로그 줄이 뒤섞이고, 한 줄만 봐서는 어느 요청에서 나온 로그인지 알 수 없습니다.

2. 설계 목표

요청 하나가 nginx에서 애플리케이션까지 같은 ID로 추적되어야 합니다. ID는 클라이언트가 아니라 서버 쪽에서 정하고, 로그에서 필드로 조회할 수 있어야 하며, 스레드가 재사용되어도 다른 요청의 로그에 ID가 남지 않아야 합니다.

3. 해결

이 문제를 생성, 전달, 기록, 조회 단계로 나누어 해결하였습니다.

1) 생성 - nginx에서 요청 ID 발급

nginx의 $request_id를 접속 로그의 맨 앞 필드로 남기고, 같은 값을 X-RequestID 헤더로 애플리케이션에 전달합니다. proxy_set_header는 클라이언트가 같은 이름의 헤더를 보내도 nginx가 만든 값으로 덮어쓰기 때문에, ID의 주체는 항상 서버입니다.

log_format main '$request_id '
                '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" '
                'upstream_time=$upstream_response_time '
                'request_time=$request_time';

location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header X-RequestID $request_id;
    ...
}

2) 전달 - 필터에서 헤더를 MDC로 이어받기

서블릿 필터가 요청 헤더의 ID를 읽어 MDC에 넣고, 이후 그 요청 스레드에서 남기는 모든 로그에 같은 ID가 붙습니다. 헤더가 없는 경우(nginx를 거치지 않는 로컬 실행 등)에는 nginx와 같은 32자리 형식으로 직접 생성합니다.

String requestId = request.getHeader("X-RequestID");
if (StringUtils.isBlank(requestId)) {
    requestId = UUID.randomUUID().toString().replace("-", "");
}
MDC.put("request_id", requestId);
MDC.put("endpoint", request.getRequestURI());
MDC.put("httpMethod", request.getMethod());

try {
    filterChain.doFilter(servletRequest, servletResponse);
} finally {
    MDC.clear();
}
  • 실행 순서: 필터에 최상위 우선순위(@Order(Ordered.HIGHEST_PRECEDENCE))를 주어 Spring Security 필터 체인보다 먼저 실행되도록 했습니다. 인증 단계에서 발생한 로그에도 같은 ID가 붙습니다.
  • 정리: 요청이 끝나면 finally에서 MDC.clear()를 호출합니다. MDC는 스레드 로컬이고 Tomcat 스레드는 재사용되므로, 정리하지 않으면 이전 요청의 ID가 다음 요청 로그에 남습니다.
  • 처리 시간: logging.execution-time.enabled 설정을 켜면 성공 응답에 한해 처리 시간(executionTime)도 같은 필드로 기록할 수 있고, 운영 환경에서는 꺼 두었습니다.

3) 기록 - 로그 패턴과 JSON 필드에 반영

운영 로그 설정에서 콘솔 패턴에는 request_id를 넣고, WARN 이상을 남기는 JSON 로그 파일에는 MDC 전체를 필드로 포함했습니다. 요청 ID가 없는 로그에는 NO-REQ가 찍혀서, 요청 스레드 밖에서 발생한 로그를 구분할 수 있습니다.

<!-- 콘솔 패턴 -->
<pattern>[%thread] %-5level [%X{request_id:-NO-REQ}] %logger{36} - %msg %nopex%n</pattern>

<!-- JSON 로그 파일 (WARN 이상): MDC 필드를 그대로 포함 -->
<providers>
    <logLevel/>
    <loggerName/>
    <mdc/>
    <message/>
    <stackTrace/>
</providers>

4) 조회 - Grafana에서 request_id로 검색

WARN 이상의 JSON 로그는 Grafana에서 필드 단위로 파싱되어 보입니다. request_id, endpoint, httpMethod가 각각 필드로 나뉘어 있어서 ERROR 로그 한 건에서 요청 ID를 확인하고, 그 ID로 nginx 접속 로그의 같은 요청을 이어서 찾을 수 있습니다.

4. 적용 결과

요청 ID가 남는 위치는 다음과 같습니다.

위치 ID가 남는 형태
nginx access.log 로그 줄의 맨 앞 필드
앱 콘솔 로그 [request_id] (없으면 NO-REQ)
앱 JSON 로그 (WARN 이상) request_id 필드 (endpoint, httpMethod와 함께), Grafana에서 필드로 조회

같은 ID로 두 로그를 각각 조회하면 한 요청이 nginx에서 어떻게 처리되었고 앱에서 무슨 일이 있었는지를 이어서 볼 수 있습니다. nginx 접속 로그의 upstream_time, request_time으로 해당 요청이 앱에서 얼마나 걸렸는지도 같은 ID로 함께 확인할 수 있습니다.

5. 회고

요청을 식별하는 값을 클라이언트가 아니라 서버 쪽에서 만들도록 한 것이 이 구조의 기준입니다. nginx가 ID를 만들고 헤더를 덮어쓰기 때문에, 로그의 ID를 외부에서 조작할 수 없습니다. 또한 스레드 재사용을 고려해 요청이 끝나면 반드시 정리하도록 하는 것이 MDC 사용에서 놓치기 쉬운 부분이라고 생각했습니다.

한계도 있습니다. MDC는 스레드 로컬이라 요청을 처리하는 스레드 안에서만 ID가 유지됩니다. 메시지 큐 컨슈머처럼 요청 스레드 밖에서 실행되는 로그에는 ID가 이어지지 않아서 NO-REQ로 표시됩니다. 이 범위 밖의 처리까지 추적해야 할 때는 메시지에 ID를 실어 전달하는 방식을 추가로 검토할 수 있습니다.
