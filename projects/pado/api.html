외부 API 호출 안정성 확보를 위한 제어·탐지·분석 체계 구축

외부 AI API의 장애가 채팅 서비스 전체의 장애로 번지지 않도록, 호출을 제어하고 장애를 먼저 감지하며 원인을 조회할 수 있는 구조를 만든 사례입니다.

  • 문제 AI 응답이 없으면 스레드가 timeout까지 묶이고, 장애는 로그를 열어 봐야만 알 수 있었음
  • 해결 Retry + Circuit Breaker로 제어, 메트릭·이메일 알림으로 탐지, JSON 구조화 로그로 분석
  • 결과 일시적 오류는 사용자에게 보이지 않고, 지속 장애는 호출을 차단하며, 장애를 알림으로 먼저 인지

1. 문제 정의

채팅 기능은 외부 AI API에 의존하기 때문에, 호출을 제어하지 못하면 사용성 저하를 넘어 서비스 장애로 이어질 수 있습니다.

  1. AI 응답 불가 시 스레드 점유
    • AI 서버가 응답하지 않으면 요청 스레드가 timeout이 끝날 때까지 묶이고, 가용 스레드가 크게 줄어들 수 있습니다.
    • timeout을 설정해도 그 시간 동안의 점유 자체는 막을 수 없습니다.
  2. 장애를 인지할 수 없는 구조
    • 별도의 알림이 없어서, 로그를 확인하기 전까지는 실패 여부와 빈도를 알 수 없었습니다.

2. 설계 목표

문제를 제어, 탐지, 분석 세 단계로 나누어 각각의 목표와 수단을 정했습니다.

단계 목표 수단
제어 일시적 오류는 흡수하고, 지속되는 장애는 호출 자체를 차단 Resilience4j Retry, Circuit Breaker
탐지 개발자가 확인하지 않아도 장애를 먼저 인지 Micrometer 메트릭, Prometheus, Grafana 대시보드, 이메일 알림
분석 어떤 요청이 언제, 어디서 실패했는지 조회 JSON 구조화 로그, Promtail·Loki, Grafana, 요청 ID

3. 해결

1) 제어 - Retry와 Circuit Breaker

  • Retry: 서버 오류가 나면 최대 3회(최초 시도 포함)까지 200ms 간격으로 재시도해서, 일시적인 오류로 사용자가 실패를 겪지 않게 합니다.
  • Circuit Breaker: 반복해서 실패하면 호출을 차단해, 응답이 없는 서버를 기다리며 스레드가 묶이는 시간을 줄입니다.
  • 예외 분류: 예외를 서버 오류(OpenAiServerException)와 클라이언트 오류(OpenAiClientException)로 나눴습니다. Retry와 Circuit Breaker 모두 서버 오류만 대상으로 해서, 요청 자체가 잘못된 경우는 재시도하지 않고 API 장애로도 집계하지 않습니다.
  • rate limit 대응: 429 응답에서는 Retry-After 헤더를 확인하도록 처리했습니다.
  • 결합 방식: 재시도를 모두 마친 뒤의 최종 결과만 Circuit Breaker에 반영되게 했습니다. 재시도 횟수만큼 실패율이 부풀지 않고, 사용자 요청 단위로 상태를 판단합니다.
  • 검증: Circuit Breaker 없이 Retry만 따로 테스트할 수 있게 분리해서, 두 기능을 각각 테스트 코드로 검증했습니다.

임계값 설정

임계값은 실제 트래픽에서 병목을 관측해야 정할 수 있는데, 운영 기간 동안 사용량이 많지 않아 조정에 쓸 데이터를 충분히 확보하지 못했습니다. 그래서 초기값은 임의로 설정했고, 이미 수집 중인 Retry·Circuit Breaker 메트릭으로 트래픽이 생기면 아래 기준에 따라 조정하도록 정리해 두었습니다.

Retry

설정 초기값 조정할 때 볼 지표
maxAttempts 3회 (최초 시도 포함) 일시적 오류가 몇 번째 시도에서 풀리는지, 사용자가 감내할 수 있는 대기 시간
waitDuration 200ms (고정) 일시적 오류가 풀리는 데 걸리는 시간, 백오프 적용 필요 여부

Circuit Breaker

설정 초기값 조정할 때 볼 지표
failureRateThreshold 50% 정상 상태에서의 실패율 분포
slidingWindowSize 2건 호출량 (윈도우가 채워지는 속도)
waitDurationInOpenState 1초 장애가 보통 얼마나 지속되는지, AI API의 timeout
permittedNumberOfCallsInHalfOpenState 2건 복구 여부를 판단하는 데 필요한 최소 호출 수

2) 탐지 - 메트릭과 알림

  • Retry와 Circuit Breaker의 메트릭을 수집해 Grafana 대시보드에서 상태를 볼 수 있게 했습니다. 메트릭이 없으면 Circuit Breaker가 호출을 차단해도 개발자는 알 수 없습니다.
  • Retry 실패율이 높아지거나 Circuit Breaker가 작동하면 이메일로 알림을 보냅니다.
  • 호출 횟수 같은 커스텀 메트릭은 @Counted 어노테이션으로 수집합니다.

3) 분석 - 로그 구조화와 조회

  • 문자열 로그를 JSON으로 구조화해 request_id, endpoint, httpMethod, logger_name, message, stack_trace 필드로 나눴습니다.
  • Promtail이 수집해 Loki에 저장하고, Grafana에서 필드 단위로 조회합니다.
  • 요청 ID로 nginx 접속 로그와 앱 로그를 한 요청으로 연결합니다. (요청 ID 추적 자세히 보기)

4. 적용 결과

상황 개선 전 개선 후
일시적인 API 오류 오류가 사용자에게 그대로 노출 재시도로 흡수
API 서버 장애가 지속 요청마다 timeout까지 스레드 점유 Circuit Breaker가 호출을 차단
장애 인지 로그를 열어 봐야 알 수 있음 대시보드와 이메일 알림
원인 분석 문자열 로그를 검색 JSON 필드 조회, 요청 ID로 nginx 로그와 연결

5. 회고

  • 외부 API를 쓰는 서비스에서는 정상 흐름보다 비정상 흐름을 어떻게 처리할지가 관건이라는 것을 느꼈습니다.
  • 제어만으로는 부족하고, 장애를 먼저 인지하는 탐지와 원인을 바로 조회하는 분석이 함께 있어야 운영 가능한 형태가 된다고 생각합니다.
  • 문제 상황을 로그에서 "추적"하는 것이 아니라 필드로 "조회"할 수 있게 된 점이 가장 체감이 컸습니다.
