새 라이브러리는 테스트로 검증한 뒤 적용: Resilience4j 학습 테스트

Retry와 Circuit Breaker를 서비스 코드에 적용하기 전에, 더미 서비스와 테스트 코드로 동작을 직접 검증한 사례입니다.

1. 문제 정의

Resilience4j는 몇 줄의 설정으로 동작이 정해지지만, 문서를 읽는 것만으로는 그 동작을 확신하기 어렵습니다. 재시도 횟수가 최초 시도를 포함하는지, 실패율은 언제부터 계산되는지, OPEN 이후 어떤 조건에서 복구되는지가 대표적입니다.

장애 대응 도구는 장애가 나기 전에 동작이 검증되어 있어야 합니다. 이해가 틀린 채로 서비스에 적용하면, 정작 외부 API에 장애가 났을 때 처음 그 동작을 보게 됩니다.

2. 설계 목표

  • 외부 API 없이 성공과 실패를 마음대로 만들어 낼 수 있는 환경에서 검증한다.
  • 상태가 바뀌는 전 과정을 사람이 눈으로 보는 대신 assert로 확인한다.
  • 이해한 동작을 실행 가능한 코드로 남겨, 이후 설정을 바꿀 때도 기대 동작을 다시 확인할 수 있게 한다.

3. 해결

1) 더미 서비스로 성공과 실패를 통제

실패 여부를 파라미터로 받는 더미 서비스에 Retry와 Circuit Breaker를 각각 적용했습니다. 실패 시에는 fallback 값을 반환하게 해서 결과를 비교할 수 있습니다.

RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(200))
        .retryExceptions(IOException.class)
        .build();
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
        .failureRateThreshold(50)
        .waitDurationInOpenState(Duration.ofSeconds(1))
        .slidingWindowSize(2)
        .permittedNumberOfCallsInHalfOpenState(2)
        .recordExceptions(IOException.class)
        .build();

더미 서비스에 적용한 설정

2) Retry 검증

  • 항상 성공하는 호출: 재시도 없이 정상 값을 반환하는지 확인했습니다.
  • 항상 실패하는 호출: 시도 횟수를 세어 Fallback response after 3 attempts가 반환되는 것을 확인했습니다. maxAttempts(3)은 재시도 3회가 아니라 최초 시도를 포함한 3회입니다.

3) Circuit Breaker 검증

상태 전이 전체를 OPEN → HALF_OPEN → CLOSED와 OPEN → HALF_OPEN → OPEN 유지 두 시나리오로 나눠 검증했습니다.

service.call(true);
assertEquals(CircuitBreaker.State.CLOSED, breaker.getState());

service.call(true);
assertEquals(CircuitBreaker.State.OPEN, breaker.getState());

assertEquals("Fallback response", service.call(false));
Thread.sleep(1100);
assertEquals("Success", service.call(false));
assertEquals(CircuitBreaker.State.HALF_OPEN, breaker.getState());

검증 코드 발췌 (일부 생략)

순서 상황 호출 결과 상태
1 실패하는 호출 1회 fallback CLOSED 유지 (호출이 2건 쌓이기 전)
2 실패하는 호출 2회째 fallback OPEN
3 OPEN 중에 성공하는 호출 실제 호출 없이 즉시 fallback OPEN 유지
4 1초 이상 대기 후 성공하는 호출 Success HALF_OPEN
5-1 HALF_OPEN에서 성공 2건 Success CLOSED로 복구
5-2 HALF_OPEN에서 실패 2건 fallback 다시 OPEN

4) 서비스 코드에 적용

검증한 동작을 기준으로 실제 OpenAI 호출 클라이언트에 적용했습니다.

  • 더미의 IOException 자리에 서비스의 OpenAiServerException을 지정해, 서버 오류만 재시도하고 실패로 집계하도록 했습니다.
  • Retry는 최초 시도를 포함한 3회에 200ms 대기, Circuit Breaker는 실패율 50%·윈도우 2건·OPEN 1초·HALF_OPEN 2건으로 시작했습니다.
  • 적용 후에도 실제 클라이언트에서 Retry가 적용되는지와 Circuit Breaker가 작동하는지를 각각 테스트로 확인했습니다.

4. 적용 결과

테스트로 확인한 설정별 동작은 다음과 같습니다.

Retry

설정 값 확인한 동작
maxAttempts 3 항상 실패하면 최초 시도를 포함해 3번 시도한 뒤 fallback
retryExceptions IOException 지정한 예외로 실패할 때 재시도

Circuit Breaker

설정 값 확인한 동작
slidingWindowSize 2 호출이 2건 쌓이기 전에는 실패해도 CLOSED
failureRateThreshold 50% 2건 모두 실패(100%)하면 OPEN
waitDurationInOpenState 1초 OPEN 후 1초가 지나면 다음 호출이 HALF_OPEN으로 전이
permittedNumberOfCallsInHalfOpenState 2 2건 성공하면 CLOSED, 2건 실패하면 다시 OPEN
recordExceptions IOException 지정한 예외로 실패한 호출이 실패율에 집계

5. 회고

  • 새로 도입하는 기술은 문서를 읽는 데서 멈추지 않고, 설정 값이 만드는 동작을 직접 실행해서 확인한 뒤 적용해야 한다고 생각합니다. 그래야 장애 상황에서 도구의 동작에 놀라지 않습니다.
  • 학습 테스트의 값은 동작을 짧은 시간에 확인하기 위한 값이었고, 서비스의 초기값으로도 같은 값을 사용했습니다. 트래픽이 생기면 지표를 보고 조정해야 합니다. (임계값 설정 자세히 보기)
  • 이 테스트는 두 기능을 각각 독립적으로 검증한 것이고, 두 기능을 함께 쓰는 방식은 서비스 코드에 적용하는 단계에서 별도로 다뤘습니다.
