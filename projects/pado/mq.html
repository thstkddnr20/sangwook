채팅 데이터 유실 방지를 위한 메시지 큐 도입

채팅 저장 방식을 동기 저장에서 Redis List 기반 비동기 저장으로, 다시 RabbitMQ 기반의 신뢰성 있는 저장 파이프라인으로 발전시킨 사례입니다.

  • 문제 애플리케이션이 Redis List로 채팅 저장을 직접 처리해, 저장 실패나 장애 시 채팅이 유실될 수 있고 추적도 어려웠음
  • 해결 저장 책임을 RabbitMQ로 위임하고 At-Least-Once + UPSERT를 적용, 처리 실패 메시지는 Dead Queue로 이동
  • 결과 재전달을 허용해 유실을 막고 중복은 UPSERT로 흡수하며, 실패한 메시지는 복구할 수 있는 구조

1. 배경: 저장 방식의 진화

사용자가 많지 않은 서비스에서는 병목이 실제로 관측되기를 기다릴 수 없었습니다. 그래서 예측할 수 있는 문제는 관측 전에 설계로 먼저 대응하는 방식으로 진행했습니다.
단계 방식 한계
1. 동기 저장 요청을 처리하는 중에 DB에 바로 저장 DB 저장의 지연이나 실패가 사용자 응답에 그대로 전파됨
2. Redis List + 비동기 저장 최근 채팅은 Redis에 두고, 초과분만 DB에 비동기 저장 초과 데이터를 앱이 직접 처리해 유실 위험이 있고, 실패를 추적하기 어려움
3. RabbitMQ 저장 책임을 MQ에 위임 (At-Least-Once, Dead Queue) 저장 시점 지연, 운영 복잡도 증가

2. 문제 정의

2단계에서는 최근 채팅을 Redis List에 두고, 넘치는 분량을 DB에 비동기로 저장했습니다.

  1. 채팅 작성 API 호출
  2. 이전 채팅을 Redis에서 조회 (부족하면 DB에서 조회)
  3. 이전 채팅을 포함해 AI API 요청
  4. 사용자 채팅과 AI 응답을 List에 RightPush, 초과분은 LeftPop
  5. 초과분을 DB에 비동기 저장

문제점

  • 초과 데이터를 애플리케이션이 직접 처리: 관리가 부실하면 채팅 기록이 유실될 수 있습니다.
  • 비동기 저장 실패를 추적하기 어려움: 유실되어도 파악하기 힘들어서, 저장에 실패한 데이터를 Redis에 다시 넣고 주기적으로 재시도하는 보완 로직까지 필요했습니다.
  • 잔여 데이터를 처리할 스케줄러가 별도로 필요: Redis List에 남은 데이터를 비워 주는 작업이 따로 있어야 했습니다.

Redis List는 캐싱에는 적합하지만, 저장 용도로 쓰면 안 된다는 결론을 얻었습니다.

3. 설계 목표

  • 데이터를 애플리케이션 안에서 직접 들고 있지 않는다.
  • 데이터를 추적할 수 있는 흐름 안에서 처리한다.
  • 유실되더라도 다시 처리할 수 있어야 한다.

4. 해결

1) Redis로 해결할 수 있는지 먼저 검토

최근 채팅 캐싱에는 Redis List를 그대로 쓰기로 하고, 저장 신뢰성을 Redis의 다른 기능으로 해결할 수 있는지 검토했습니다.

후보 검토 결과 판단
Redis Pub/Sub subscriber가 수신하지 못하면 메시지가 유실되고, ACK와 재처리 메커니즘이 없음 제외
Redis Streams append-only 로그라 재처리가 가능하고 유실도 막을 수 있음. 다만 소비 후에도 기본적으로 메시지가 남는데, 채팅은 "저장"보다 "처리"가 목적이라 처리가 끝나면 가지고 있을 필요가 없음 제외
RabbitMQ 전달 신뢰성(Publisher Confirm)과 처리 보장(ACK), 처리 후 제거, 실패 시 재시도를 모두 만족 채택

2) RabbitMQ 도입 후 흐름

  1. 채팅 작성 API 호출
  2. 캐싱된 채팅을 더해 AI API 요청
  3. 새로 받은 응답으로 캐시 갱신
  4. 저장용 메시지 발행 (Flush Queue)
  5. Consumer가 Flush Queue의 메시지를 처리해 DB에 저장

캐시 갱신을 저장보다 먼저 두었습니다. 저장이 큐를 거치며 늦어지더라도 사용자는 항상 최신 채팅을 볼 수 있어야 하기 때문입니다.

3) 메시지 유실 방지 전략

채팅 유실은 반드시 막아야 했기 때문에 At-Least-Once를 채택했습니다. 최대 한 번 전달하는 At-Most-Once는 유실될 수 있고, 정확히 한 번 전달하는 Exactly-Once는 구현 복잡도가 커서, 중복을 허용하되 최소 한 번은 처리되는 방식이 적합하다고 판단했습니다.

유실이 생길 수 있는 지점마다 대응을 두었습니다.

구간 대응
발행 (Producer) Publisher Confirm으로 브로커가 정상 수신했을 때만 성공으로 처리하고, CorrelationData로 발행 결과를 추적합니다. 실패하면 3회 재시도 후 fallback으로 DB에 직접 저장하고, 라우팅·confirm 실패는 에러 로그로 남깁니다.
소비 (Consumer) Manual ACK를 적용하고, DB 저장을 트랜잭션으로 묶어 커밋이 끝난 뒤에 ACK를 보냅니다. 커밋 전에 ACK하면 커밋이 실패했을 때 메시지가 사라지기 때문입니다. 사용자 채팅과 AI 응답은 하나의 메시지에 담아 함께 저장합니다.
소비 실패 처리 중 예외가 나면 실패 사유를 메시지 헤더에 담아 Dead Queue로 이동합니다.
중복 전달 채팅 PK는 변하지 않는 값이므로 DB에 UPSERT해서 중복 저장을 막습니다.

Dead Queue

Consumer 처리 중 예외가 나면 채팅이 유실될 수 있어서 Dead Queue를 도입했고, 쌓인 메시지는 DB로 옮겨 복구할 수 있습니다. 처음에는 실패용 큐를 하나 더 두었지만, 소비 실패 시 바로 Dead Queue로 보내도록 단순화했습니다.

5. 적용 결과

  • 데이터 저장 책임을 별도 인프라(MQ)에 위임해, 애플리케이션이 처리 중인 데이터를 들고 있지 않고 안전하게 종료할 수 있게 되었습니다.
  • At-Least-Once로 유실을 막고, 저장 시 UPSERT로 중복 데이터를 처리했습니다.
  • 소비하지 못한 메시지는 Dead Queue로 이동해 복구할 수 있는 구조가 되었습니다.

6. 트레이드 오프

  • 최종 저장 시점이 지연됩니다. Redis 캐시로 최신 채팅을 보여 주어 사용자 경험을 보완하지만, 메시지가 Dead Queue로 이동하면 DB 반영이 늦어져 일부 기록이 일시적으로 보이지 않을 수 있습니다. 이는 유실이 아닌 지연이고 재처리로 복구됩니다. 즉시 일관성 대신 최종 일관성을 선택했습니다.
  • 운영 복잡도가 증가합니다. Dead Queue를 별도로 관리하고 소비되지 못한 메시지를 처리해야 합니다. 애플리케이션 내부에서 처리하던 단순한 구조에서 벗어나, 관측성 확보와 운영 부담이라는 대가가 생겼습니다.

7. 회고

  • 병목은 트래픽이 있어야 보이지만, 유실은 트래픽과 무관하게 장애 한 번으로도 생깁니다. 그래서 관측을 기다리지 않고 예측 가능한 문제를 설계로 먼저 막는 것이 사용자가 적은 서비스에서의 현실적인 선택이었습니다.
  • 성능도 중요하지만, 안정성을 위해서는 데이터 유실을 막는 구조가 우선이라는 것을 깨달았습니다.
  • 애플리케이션 내부에서 직접 처리하는 구조는 분산 환경에서 한계가 있습니다. 유실이 생겨도 추적하기 어렵고, 내부 스케줄러가 중복 실행되면 데이터가 중복 저장될 위험이 있습니다. 저장 책임을 MQ에 위임하고 Dead Queue로 실패 메시지를 보관해, 처리의 신뢰성과 복구 가능성을 함께 확보했습니다.
